Task queue (evi task)

Overview

The task queue is how eVi works on a repository, itself included, without marking its own homework. The director (you) files a task with acceptance criteria and the checks that prove them. evi task start runs eVi on it in a git worktree of its own under the implementer policy, allowed to change only the files the task names. eVi runs the checks itself and stops at implemented. Only the director's signed evi task verify or evi task reject gives the task a verdict.

  • A task is a file in the repository. Each task is one .evi/tasks/<id>.toml, tracked in git, so the queue is shared like any other file.
  • eVi stops at implemented. A start never commits, merges or sets a verdict. It leaves the work uncommitted in the worktree of branch task/<id>, writes a run report, and sends the task back to open when the run or a required check failed.
  • Verdicts are signed. verified and rejected count only with an attestation made with the director's key (The director's attestation key). A task file someone edited to say verified reads unverified (unsigned).
  • Director tooling refuses where an agent may be. evi task verify, evi task reject and evi attest refuse, and write nothing, in any process an eVi agent may have started.
  • Every run leaves evidence. A start writes an evidence bundle (the diff, eVi's own run of the required checks, a redacted transcript excerpt), and the verdict signs its hash.

An MCP client can drive the queue too: evi mcp serve --categories agent serves tools to file, start, follow, steer and cancel tasks, but none that gives a verdict (Over MCP). The web app doesn't offer the queue.

How it works

What a task is

A task is a TOML table. evi task new writes the fields the director files; evi task start and the verdict commands fill in the rest.

FieldWhat it holds
idT<n>, the next free number, unless you give one with --id: 1 to 64 letters, digits, _ or -, not a Windows device name (con, nul, com1 …), unique whatever its case. It names the file and the branch, task/<id>.
titleWhat the task is, in one line. Required.
statusopen, claimed, implemented, needs_review, verified or rejected (see States and leases).
whyThe bug or the need.
hintsHow to approach it: your guidance for the implementer (where to look, what to reuse, what to avoid), shown after why in its prompt. A string; "" for none.
acceptanceThe acceptance criteria, a list of strings.
files_in_scopeGlobs relative to the repository: the only files a start may write (What a task may change). A protected file in the worktree (EVI.md, a CI workflow) becomes writable only when an entry names it explicitly, as --scope does for evi run --policy implementer. An empty, absolute or .. entry is refused, and a task without any can't be started.
required_checksThe commands that prove the task: each a command line, split the POSIX way (use / in paths), or an argv array. A plain string instead of a list is refused.
implementerWho should implement it, as a hint: evi-local, evi-frontier or director. Nothing enforces it.
createdWhen the task was filed (UTC).
attemptsHow many starts ran, successful or not.
backend, modelWhat the latest start ran on.
worktree, branch, baseThe task's worktree, its branch and the commit the branch started from. A verify reviews the diff from base.
evidenceThe evidence bundle's path, "" until there is one.
evidence_summaryThe bundle's hash (what a verify signs), files changed, insertions, deletions, checks passed and failed, the junit totals when a pytest check ran, and why no check ran when none did. A new task has none: the first bundle adds it.
reviewer_notes{at, verdict, note} entries, from a reopen, a verify or a reject.
lease{holder, expires_at} while the task is claimed, empty otherwise.
last_resultThe latest start's {stop_reason, exit_code, report, summary, out_of_scope, out_of_scope_more}. The summary is the first line of the answer, with control characters removed. out_of_scope lists the files the branch changed outside files_in_scope (at most 200; out_of_scope_more counts the rest and is there only when there are more); it is left out when git couldn't tell.
attestationOnly on a signed task: the director's signature (Verify and reject).

A new task looks like this:

id = "T1"
title = "Fix the parser's off-by-one"
status = "open"
why = "tokens at the end of a line are dropped"
hints = "the loop is in tokenize(); keep its signature"
acceptance = ["a trailing token is kept"]
files_in_scope = ["evi/parser.py", "tests/test_parser.py"]
required_checks = ["python -m pytest -q tests/test_parser.py"]
implementer = "evi-local"
created = "2026-10-17T10:42:07Z"
attempts = 0
backend = ""
model = ""
worktree = ""
branch = ""
base = ""
evidence = ""
reviewer_notes = []

[lease]

Unknown fields are kept, so you can add your own. Every value has to read back from TOML exactly as it was written (TOML has no null), because the attestation signs the values as parsed.

What a task may change

A start is confined to the task's files_in_scope: the implementer policy denies a write to any other file in the worktree. That covers write_file, edit_file, every file an apply_patch call names, a file an output redirect in a command line writes (> out.txt; the null device is fine), and the files a command rewrites: ruff format, and ruff check with a fixing option such as --fix. Such a command must name its files, each in scope; given a folder (ruff format .), a wildcard or no file at all, it is denied with name the files instead. Reading, running the tests and linting are not confined: they work on any file. The full rules are in Implementer policy → Confined runs.

The model sees each denial as the tool result, and it says what to do:

'docs/notes.md' is not in the task's files_in_scope: change only those files, and list this one as a concern in your hand-off instead (files_in_scope: evi/parser.py, tests/test_parser.py)

The prompt says so up front too. A task with no files_in_scope could change nothing, so evi task start refuses it (exit 2) before it claims anything, and evi task new without --scope prints a note saying so.

How an entry matches a file (the path relative to the repository, with / between folders; case doesn't matter on Windows):

EntryCovers
evi/parser.pythat file
tests/fixtures or tests/fixtures/everything below that folder
pages/[id].tsxthat file: an entry is first taken literally, so brackets in a name are just characters
evi/*.pyevery .py file under evi/, in subfolders too: * crosses folders
*.mdevery .md file in the repository
**/*.py, tests/**/test_*.pyas in a .gitignore, a **/ also matches no folder: calc.py at the top, tests/test_x.py
.every file in the repository

Past the literal match, an entry is a glob (*, ?, [abc]) over the whole path, or over a folder the file is in. A broad entry still opens no protected file: only an entry that names one explicitly does (Protected files).

What the policy can't see is caught afterwards. A command can still write a file on its own: a test that leaves an output file, a fix = true setting in the repository's ruff configuration. So after the run, eVi lists every file the branch changed, committed or not, that no entry covers (untracked files in a cache folder such as __pycache__ or .pytest_cache left out). The list is out_of_scope in the run report's task section and in last_result, and evi task show prints it (out of scope: …, or none). It never changes the outcome. evi task verify is the gate: it works the list out again on the branch it signs, and refuses while it isn't empty unless you say why with --allow-out-of-scope REASON.

Where the files live

The queue is <repo>/.evi/tasks/, where <repo> is the repository's main checkout. evi task finds the same queue from any folder of the repository, a task's own worktree included. The queue is whatever .evi/tasks/ holds in the main checkout's working tree, so commit a task file on the branch you share the queue on.

Task files are tracked so that the queue travels with the repository: a teammate who pulls sees the same tasks, and a task's record, its attestation included, is in the history. eVi's own .gitignore ignores the rest of .evi/:

.evi/*
!.evi/tasks/
!.evi/bug-ledger.jsonl
!.evi/REVIEW.md
!.evi/review-rules.md
*/**/.evi/

The rule is .evi/*, not .evi/, because git can't re-include a file inside an ignored folder. Both rules are anchored to the repository's top level, so */**/.evi/ keeps an .evi/ folder deeper down ignored (a session started in a subfolder leaves one there). The bug-fix ledger (record_fix, search_fixes) and the review guidance (evi review) are shared the same way. Another repository whose task queue you want in git needs the same lines. Without them, .evi/tasks.lock shows up in git status; with a plain .evi/ rule, git ignores the task files too.

Every change to a task holds a lock on .evi/tasks.lock, so of two concurrent claims one wins and the other sees the claim. A write goes to a temporary file under .evi/ and then replaces the task's file, so a crash leaves either the old file or the new one. A write that can't be made, or a lock still held after 15 seconds (another eVi is changing the task queue), is an error and leaves the old file as it was.

An agent's write to a task file goes through the protected-path check: .evi/** is protected, so the write asks in every mode, yolo included, and is denied when nothing can answer. The implementer policy never opens .evi/tasks/**, whatever the task's scope says. And a written verdict counts for nothing without the director's signature.

Run reports and evidence bundles are not in the repository. They go under eVi's home (see What evi task start does).

  • claim makes a task claimed, with a lease: a holder (default <user>@<host>) and an expiry (--ttl minutes, default 240). The same holder claiming again renews the lease.
  • Another holder's live lease refuses a claim, a release and a start, unless you pass --force. An expired lease, or one whose expiry can't be read, can be taken by anyone.
  • evi task start claims the task itself and clears the lease when it finishes. The task ends implemented when the run finished and every required check passed, otherwise open. Either way the attempt is counted.
  • submit hands an implemented task to review (needs_review). Only a needs_review task can be verified or rejected.
  • reopen sends an implemented, needs_review, verified or rejected task back to open and drops its attestation, which no longer applies. To run an implemented task again, reopen it first.
  • A step the status doesn't allow is refused (exit 2), and so is any write that sets a verdict without the director's attestation, or changes a verified or rejected task other than by reopening it.

What evi task start does

evi task start <id>:

  1. Marks its own process as an agent host (EVI_AGENT=1), as every agent-hosting entry point does, so everything the run starts carries the mark (The director's attestation key).
  2. Refuses an untrusted repository. Run evi trust there from your own terminal first: the implementer policy runs no commands and no checks in an untrusted folder, so nothing could prove the task.
  3. Reads the task (its required checks must parse, and it must have files_in_scope, all inside the repository) and claims it with a lease of --ttl minutes. Someone else's live lease refuses the start unless you pass --force.
  4. Opens the task's worktree: branch task/<id> in <repo>/.worktrees/task__<id>, created the first time from --base (default [worktree] base_ref, else HEAD), reused on later attempts, and locked while the run goes on. A branch checked out anywhere else, your main checkout above all, is refused. A lock left by a start on this machine whose process is gone is taken over; any other lock refuses the start. The worktree, branch and base go into the task.
  5. Builds the agent in the worktree, on --backend and --model or your configured backend. The worktree's EVI.md and .evi.toml apply (the repository is trusted). The agent is held to the implementer policy, confined to the task's files_in_scope (What a task may change), with its required checks allowed as exact commands, and nothing asks: every call is allowed or denied. The verify gate is on, even with [checks] verify = "off", and the required checks join [checks] commands for the run, so the model sees a failing check before it can finish. A delegate CLI-agent backend (codex, gemini, amp, qwen, copilot) is refused as the [llm] backend, as a [models] *_backend or as --backend, whatever [llm] allow_cli_agent_unattended says: it runs its own tools, outside the policy.
  6. Runs the prompt it builds from the task: the title, why, your hints (How to approach it:), acceptance criteria, files in scope, required checks and the implementer contract in EVI.md. The implementer is told that a write outside the files in scope is refused and belongs in its hand-off as a concern, and never to commit, push or change the task's status. The run takes at most --max-turns model round trips (default 30).
  7. If the run ended done, runs each required check itself in the worktree (with [checks] timeout). That run is the ground truth: the model saying the tests pass doesn't count.
  8. Lists the files the branch changed outside files_in_scope (out_of_scope, above). A list git can't produce is a note, and the outcome stands either way.
  9. Writes the run report to <eVi home>/tasks/<repo key>/<id>/<attempt>/report.json, where the repo key is a hash of the main checkout's path. It is evi run's run report plus a task section: the id, attempt, repository, branch, base, outcome, stop reason, exit code, the required checks' results, files_in_scope, out_of_scope (at most 200 paths) and out_of_scope_more (how many more), both null when git couldn't tell.
  10. Collects the attempt's evidence bundle, whatever the run's stop reason, in <eVi home>/evidence/<repo key>/<id>/<attempt>/: the worktree's diff against the base, eVi's own run of the required checks again (a pytest one with its junit report; none when the run stopped before its checks, and a Ctrl+C stops them), a redacted excerpt of the run's transcript and report.json. A bundle that can't be collected is a note; the run is recorded all the same, without evidence.
  11. Records the attempt, backend, model, last_result (with out_of_scope), evidence and evidence_summary, and leaves the task implemented or open. When eVi's own run of a required check fails, the task's stop reason is checks_failed (exit 5) even if the run itself ended done. The worktree is unlocked.

The hand-off, the model's answer, goes to stdout; a character the terminal can't show (a lone surrogate from a model's broken emoji) goes out escaped (\ud83d). The verify gate's check lines, the worktree summary, each required check, the outcome, any note, the report's path and the evidence bundle with its summary go to stderr. The files changed outside the scope are not printed: evi task show has them. Nothing is merged or committed, and the checkout you work in is never touched.

A refusal before the run (exit 2) means nothing ran and the task is exactly as it was before. A failure while building the agent counts as the run's error: exit 1, the attempt counted, the task back to open. If the outcome can't be written to the task file, the exit code is at least 1 and a note says so; when the task is still claimed by you, evi task release <id> puts it back to open.

The prompt doesn't include the reviewer notes. When you send a task back, put what has to change in its why, hints or acceptance, and widen its files_in_scope if the work needs another file. An open task's file is plain TOML with no signature, so you can edit it.

Over MCP (evi mcp serve)

evi mcp serve --categories agent gives an MCP client (the director's own agent, say) the queue's tools: task_create, task_list, task_show and task_start, then run_status, run_steer, run_cancel and run_result for the run a start queues. See MCP → The agent category for each tool, the transport rules and what may be served beside it.

A run started this way goes through the steps of evi task start, one run at a time, and records the same things: the attempt, backend, model and last_result, the run report under <eVi home>/tasks/ and the evidence bundle under <eVi home>/evidence/. What differs:

  • The claim is held by <user>@<host> (evi mcp serve, pid N), with a 10-minute lease renewed every 2 minutes once the run's agent is built. A server that dies leaves a claim that runs out within 10 minutes, after which anyone can start the task.
  • A cancel (run_cancel, or a run past [tasks] max_run_minutes, or the server closing) ends the run interrupted, unless its outcome is already being recorded: the task goes back to open with the attempt counted, and its bundle has the diff and the transcript but no checks run, with the reason in checks_skipped. A queued run that is cancelled never claims its task.
  • A task without files_in_scope is still queued by task_start, then ends in the error state with the reason, never having claimed the task (evi task start refuses it before anything).
  • No verdict. No tool submits, verifies, rejects or reopens a task. The server runs as an agent's process, where the director key isn't read, so task_list and task_show show a signed verdict as unverified (no director key here …). Review, commit, submit and verify from your own shell.

Verify and reject (director only)

eVi never marks its own work verified. A verdict is an attestation: an HMAC-SHA256 under the director's key over the task record (every field but the attestation), the branch head, the evidence bundle's hash, the verdict, the review rounds and the review gate's result. Only director tooling run from the director's own shell makes one, and the queue refuses to write a verdict without one.

Refused where an agent may have started the process. evi task verify and evi task reject exit 2, writing nothing and running no review, when EVI_AGENT is set, inside an evi chat session (EVI_INTERACTIVE=1), when an eVi process runs above them (evi chat, evi serve, the desktop app's server), or when the process's own command line isn't evi task verify|reject or evi attest (code calling eVi's signing functions some other way). In an eVi session, a tool call that runs them is denied in every mode as well (The director's ground).

What evi task verify checks. Before anything is signed:

  1. The task is needs_review (evi task submit it first).
  2. It has a branch and a base, so it has been started.
  3. A worktree has task/<id> checked out (git's worktree list decides, not the path in the task file), it is at the branch's head, and it has no uncommitted or untracked files. The implementer never commits (the policy allows only read-only git), so review the agent's work and commit it on task/<id> in its worktree first. Otherwise the attestation would sign a head without the work, and the review would see an empty diff.
  4. The task's base is a commit the review can trust. The field comes from a tracked file, so it isn't taken as it is: it is resolved to a commit in the main checkout, and that commit must be an ancestor of the branch head and not the head itself, where the diff would be empty and pass any review.
  5. The branch changed no file outside files_in_scope. Verify works this out again on the branch it is about to sign, against that base commit, rather than trusting the out_of_scope list the run recorded: the task file is tracked, so that list could have been edited, and you may have dealt with it since. While files are outside, verify refuses (exit 2), naming up to ten of them: undo them on the branch, widen the task's files_in_scope, or pass --allow-out-of-scope REASON to sign anyway. The reason, with the files, goes into the reviewer notes (verdict out_of_scope_allowed) before signing, so it is signed too. A reason given when nothing is outside is not recorded; a note on stderr says so.
  6. The evidence, if the task names any, is a bundle eVi wrote (which folders a task may name), unchanged since it was collected: its hash matches the one evidence_summary recorded. After a change, evi evidence collect <id> collects it again.
  7. The review gate runs: evi review --multi --exit-code on the diff from that base commit to the branch head, in the worktree (the reviewers' tools read that tree too). It needs a working backend. Each lens marks a finding BLOCKING: (the change must not ship with it) or SUGGESTION:; the gate blocks on a BLOCKING: finding, on a lens that failed or said nothing, and on any file:line from a lens that used no marker, never on suggestions. Blocking findings print the review on stderr and exit 1, unless --reason says why to sign anyway; that reason is recorded in the attestation and in the reviewer notes.
  8. You confirm on the terminal: the prompt names the head, the evidence, the rounds, the review result and any override. --yes skips it from your own shell. With no terminal and no --yes, verify refuses (exit 1).
  9. The director key signs (no key: exit 1, evi attest init makes one), and the signed task is written back only if the file hasn't changed since it was read (otherwise exit 2: run the command again).

evi task reject needs a needs_review task that has a branch, and --reason, which goes into the reviewer notes before signing, so it is signed too. There's no worktree, base or review check, but an evidence path eVi won't read refuses it as well. evi task reopen then sends the task back for rework.

--rounds N (default 1) records how many review rounds the task took.

How a task's status reads

evi task list and evi task show show the status as the attestation has it. A verdict counts only with a valid attestation from this machine's director key, at the branch's current head, over the record and the evidence as they are now.

ShownWhy
open, claimed, implemented, needs_reviewThe status as written.
verified, rejectedA valid attestation.
unverified (unsigned)The file claims a verdict (in any case, with look-alike letters or invisible characters too) and carries no attestation: it was edited by hand or written by something other than verify or reject.
unverified (invalid signature: the task record changed after it was signed)The task file was edited after it was signed.
unverified (invalid signature: the evidence changed after it was signed)The evidence bundle changed, or its path is one eVi won't read.
unverified (invalid signature: …), other reasonsA forged or malformed signature, or one made with another director key.
unverified (stale: signed at <commit>, the branch is now at <commit>)The branch moved on after it was signed, or an older verified file was restored from history.
unverified (no director key here to check the signature)This machine has no director key, or the command runs where an agent may have started it, where the key isn't read.
unverified (unrecognised status …)A status that isn't plain ASCII.
<status> (an earlier attestation no longer applies)A status other than a verdict that still carries an attestation (eVi drops it when it reopens a task).

When the branch no longer exists (a merge deleted it, say) or can't be read, its head can't be compared, and only the record and the evidence are checked. In --format json, status is the word in the file and label is what counts.

The director key (evi attest)

evi attest init creates the director key: 32 random bytes in the OS keyring (service evi-director) when the optional keyring package works, else in <eVi home>/director/director.key, readable only by you. It asks you to confirm on the terminal, or takes --yes from your own shell. An existing key is an error (exit 1) unless you pass --rotate, which replaces it and makes every attestation signed so far invalid.

evi attest status prints the key's id and where it is kept, never the key itself.

The key is an HMAC key, so an attestation can be checked only where the key is. On another machine, or in CI, a verified task reads unverified (no director key here …). See The director's attestation key for where the key lives, what agents can't do with it, and the limits.

Usage

The director loop

From your own terminal, in the repository:

evi attest init        # once per machine
evi trust              # once per repository
evi task new --title "Fix the parser's off-by-one" --acceptance "a trailing token is kept" --scope evi/parser.py --scope tests/test_parser.py --hint "the loop is in tokenize(); keep its signature" --check "python -m pytest -q tests/test_parser.py"
evi task start T1 --backend local
evi task show T1
git -C .worktrees/task__T1 status
git -C .worktrees/task__T1 add -A
git -C .worktrees/task__T1 commit -m "fix(parser): keep a trailing token"
evi task submit T1
evi task verify T1
evi evidence commit-body T1 > msg.txt
git merge --no-ff -F msg.txt task/T1

--backend local names a saved backend (evi backend list); leave it out to use your configured one. Review the work in .worktrees/task__T1 (and the hand-off, the report and the evidence bundle) before you commit it; evi task show T1 says whether the run changed anything outside the task's files_in_scope (out of scope:), which verify won't sign without your reason. evi task submit collects the bundle again from what you committed. If it isn't right, evi task reopen T1 --reason "…", adjust the task's why, hints or acceptance, and evi task start T1 again: the next attempt carries on in the same branch and worktree. To turn it down for good, evi task reject T1 --reason "…". Once verified, merge task/T1 with the message evi evidence commit-body prints: it ends with the provenance trailers, Verified-by and Attestation included (Commit messages). Don't commit on task/T1 after verifying, or the signature no longer matches its head. evi worktree prune then removes the worktree.

Commands

Every evi task command finds the queue from the current folder. A refused request (a bad id or flag, a step the status doesn't allow, someone else's lease, a write that can't be made) prints error: … on stderr and exits 2.

evi task new files a task, open, in .evi/tasks/<id>.toml. --title TEXT (required, unless --from gives one), --why TEXT, --hint TEXT (repeatable, one line each, hints), --acceptance TEXT (repeatable), --scope GLOB (repeatable, files_in_scope: the only files a start may write; without one a note on stderr says evi task start will refuse the task), --check COMMAND (repeatable, required_checks), --implementer evi-local|evi-frontier|director, --id ID (default: the next T<n>) and --from FILE, a TOML file with the same fields (hints as a string or a list of strings), which the flags override (run bookkeeping and any attestation in it are dropped).

evi task list lists the tasks with their status as it reads. --format text|json (-f); JSON gives id, title, status, label, implementer, branch and attempts per task. A task file that can't be read is a warning on stderr.

evi task show ID shows one task: its fields (hints included), the status as it reads, the lease, the last result and report, what the last start changed outside files_in_scope (out of scope: …, or none), the evidence bundle and its summary, the reviewer notes, the attestation and the file. --format json gives {task, label, path}.

evi task claim ID claims an open task, or one whose lease ran out. --holder NAME (default <user>@<host>), --ttl MINUTES (default 240), --force to take over someone else's live lease.

evi task release ID gives a claimed task back: it is open again. --holder NAME, --force.

evi task submit ID hands an implemented task to review (needs_review). First it collects the task's evidence bundle again, from the worktree git has task/<id> checked out in (so it holds the work you committed), running the required checks once more, and records it with the status. A bundle that can't be collected is a note on stderr, and the task keeps the evidence it had. --director also takes an open task whose work you finished yourself after the implementer's attempts: commit it on task/<id> first (a branch with nothing beyond its base is refused). A reviewer note says the director finished it, so the verdict signs that. It is refused in any process an eVi agent started.

evi task reopen ID sends an implemented, needs_review, verified or rejected task back to open, dropping any attestation. --reason TEXT is kept in the reviewer notes.

evi task start ID runs the task (What evi task start does). --backend NAME (a saved backend, evi backend list), --model ID, --base REF (where a new task branch starts), --max-turns N (default 30), --ttl MINUTES (default 240), --force to take over someone else's live lease.

evi task verify ID (director only) signs a needs_review task as verified (Verify and reject). --reason TEXT (sign although the review gate reports blocking findings), --allow-out-of-scope REASON (sign although the branch changed files outside files_in_scope), --rounds N (default 1), --yes.

evi task reject ID (director only) signs a needs_review task as rejected. --reason TEXT (required), --rounds N, --yes.

evi attest init (director only) creates the director key. --rotate, --yes.

evi attest status shows whether this machine has a director key.

evi evidence collect ID, evi evidence commit-body ID and evi evidence prune collect a task's bundle on demand, print its commit message and remove old bundles; see Evidence bundles.

A start that ends anywhere but implemented leaves the task open; its exit code says why, as evi run's does. See Troubleshooting for the refusals.

Notes / limits

  • Only verify, reject and evi attest are director tooling. The other evi task commands change unsigned state. None of them can make a verdict, and a reopen drops one rather than forging one.
  • A verdict checks only where the key is. See The director key.
  • The review gate reads the branch's own guidance. It loads .evi/REVIEW.md (the tracked checklist), .evi/BUGBOT.md (untracked guidance of your own, when the worktree has one) and .evi/review-rules.md from the task's worktree, so when the diff changes those files, read that part yourself.
  • Check the base the review ran against. Verify proves the task's base is in the branch's history, not that it is the commit the branch started from. The confirmation prompt names the base the review gate used.
  • Deleting the highest-numbered task file frees its number. The next evi task new gets the same T<n>, and its start carries on in the old task/T<n> branch and worktree. Remove that worktree and branch first.
  • The same OS user. The agent runs as you, so these checks keep it from verifying its own work by accident or unnoticed, not from a determined attempt. See the limits in The director's attestation key.
  • A guardrail, not a sandbox. The required checks run the repository's code in the worktree; see Implementer policy. The scope works the same way: the policy stops the writes it can see in a call, and what a command writes on its own reaches the branch and shows up in out_of_scope, where verify stops it.
  • * crosses folders in a scope entry. evi/*.py covers every Python file below evi/, not only those directly in it. Name files, or a folder, when you mean less.
